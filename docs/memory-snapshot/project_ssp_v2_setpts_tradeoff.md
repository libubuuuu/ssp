# 背景

P221 V2 fal seedance r2v 端点输出比 input 短固定 0.083s(2 帧 @24fps),5 sample 全一致(2026-05-10 probe 4s/5s/6s/7s/8s)。

commit 3 砍单档时选定 B'' 方案处理偏差:**ffmpeg setpts 把 fal 输出从 (N-0.083)s 拉伸到精确 N s**,音频用 atempo 同步拉伸。

# B'' 已知副作用(选这条路就接受)

时间拉伸 = 视频整体播慢 1%(7.917s → 8s 是 1.05% 拉伸)。具体影响:

1. **人说话:语速慢 1%** — 普通话 5字/秒 → 4.95字/秒,无人能察觉(听力鉴别阈值 ~3%)
2. **背景音乐:节拍偏 1%** — 比如 120 BPM → 118.8 BPM。
   - 大众用户察觉率:几乎为 0
   - 对节拍敏感的人(音乐人/DJ)可能听出"慢半拍"
3. **快速运动场景:有微妙的慢动作感**
   - 拳击/舞蹈/赛车镜头可能感觉"力道不足"
   - 但 1% 远低于电影行业的 4%(PAL 24→25fps)行业标准
4. **跟原视频对比:可能感觉"哪里怪怪的"**
   - 用户传 30s 视频,处理后还是 30s,但帧逐帧对比有 1% 偏移
   - 大部分用户不会逐帧对比

# 为什么仍选 B''(对照其它方案)

- B 全段末帧 hold:多段累积 N 个 80ms 停顿,**用户察觉率显著高于 B'' 的 1% 拉伸**
- B' 只末段 hold:总长比原视频短 0.083×(N-1)s,音轨不齐有静音/截断
- D 段间 crossfade:实现复杂、xfade 编码慢、总长也短

B'' 是**已知副作用最不显眼的方案**,不是"想当然简单"。

# 自适应方案评估(不今天做)

理论上"检测剧烈运动/高节拍 → 切 B'/D"听起来好,实际:

**为什么不做自适应**:
- 检测算法本身复杂(motion_score + audio onset detection,每段一次额外 ffmpeg 分析)
- 误判成本:漏检剧烈运动 → 出问题;过度敏感 → 多数视频走 B'(体验不一致)
- 工程上把"用户感知差异 1%"换成"代码复杂度 +50%"不划算

**降级触发条件(出问题再启用)**:

只有以下任一发生才考虑切方案:

| 触发 | 动作 |
|------|------|
| 用户投诉"音乐节拍不对"且能复现 | 该用户的视频走 D(段间 crossfade),保持音轨原速 |
| 用户传"动作 +音乐"组合视频投诉率 > 5% | 全局切 B'(只末段 hold),牺牲精确总长 |
| fal 后续修复 0.083s 偏差(返回精确 N 秒) | 取消所有拉伸/补帧逻辑 |

**监控指标**(公开后挂):
- "用户对成片不满意"的反馈率(前端加 thumbs down 按钮)
- 视频里检出"音乐"的占比(初期 ffprobe 看是否有音轨即可)
